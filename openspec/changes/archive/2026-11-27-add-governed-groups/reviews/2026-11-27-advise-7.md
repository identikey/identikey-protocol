## Independent take

Written before opening design.md or tasks.md, from the proposal's Why, the requested living-standard sections, and the auth registry and encodings:

1. I would pin bare 32-byte keys to Ed25519 and forbid tagged Ed25519 aliases.
2. I would pin canonical key encoding, equality, and ordering across every key-bearing structure.
3. I would preserve member-key uniqueness and separation from witness and exit keys.
4. I would require existing Ed25519 entries, state digests, XIDs, and bundles to retain identical bytes.
5. I would make algorithm acceptance a mechanism contract, not infer it from a tag alone.
6. I would refuse tagged keys under the current mechanisms, even when their registry tag is recognized.
7. I would require an adoption entry to remain verifiable under the old signature, actor, receipt, and size rules.
8. I would require old verifiers to detect unknown mechanisms before interpreting new policy fields and then establish a durable stop.
9. I would refuse unknown-mechanism founding entries without requiring an old verifier to parse future signatures.
10. The tradeoff is a constrained transition using old credentials, in exchange for preserving existing bytes while allowing new mechanisms to define future cryptography.

## Comparison and steelman

The author answers these concerns. I examined `git diff 3137bc5 HEAD` and the amended sections in place. The strongest case for this choice is that it specifies a common future key representation without charging existing groups for tags or pretending that a registry entry supplies a verification mechanism. Always tagging Ed25519 would change every containing commitment. Leaving all future representations unspecified would preserve today's bytes too, but would lose the shared type and comparison rule K1 asks for.

**Canonical keys and invariants.** Standard §2.2 separates CBOR byte strings from maps without ambiguity, forbids tagged Ed25519, closes the map, and imports the registry's raw encodings. Deterministic encoding fixes map order. Equality and sorting use the whole encoded key, including the algorithm for tagged keys. Thus the roster uniqueness and member/witness/exit separation rules (§7) have an exact comparison operation; a tagged Ed25519 alias cannot bypass them. For today's keys, the common `58 20` prefix makes encoded-key order identical to raw-key order. The bundle's `keys` array remains signature wire order, explicitly excepted from body/state sorting in §13. Future algorithm profiles must validate their canonical key bytes; merely having a tag never makes a key admissible.

**Unchanged v1 bytes.** Every admissible v1 key remains the same 32-byte CBOR string. No enclosing body, policy, state, core map, signature assertion, or bundle field changes its encoding. Therefore the state digest, unsigned entry bytes, entry hash, signing digest, and founding XID remain unchanged for identical existing inputs. Bundles likewise retain their bytes and key order. This claim concerns existing default-only objects; it does not claim a future tagged-key state has the old state's digest. Adopting a mechanism changes later state while leaving the original founding XID intact.

**An adoption traced through the boundary.** Consider a valid chain through sequence 4. At 5, a `group.policy` entry names a new authorization mechanism. Existing Ed25519 members sign in the §4.3 layout, with the old proposer's raw key in `actor`, within v1 limits, and the outgoing witness supplies the ordinary Ed25519 receipt. Standard §15 reads the mechanism before closed-map or new key validation. It leaves the rest of the policy body uninterpreted, then checks all four establishment conditions: the old envelope/parent/sequence, every signature and the old proposer, the prior policy quorum, and the prior witness receipt. It stores unsupported at 5 and authorizes nothing from state 4, even on later delivery of a shorter bundle. New policy fields or tagged keys inside that opaque body do not defeat this path.

The fixed signature layout is a real transition constraint: a new-algorithm signature added to this adoption envelope would fail establishment, even alongside sufficient old signatures. It must not be used to claim a durable v1 stop. The contract already requires current-mechanism signers and all four checks, rather than promising that arbitrary future evidence establishes the transition. A later mechanism can retain old member keys for adoption and introduce new member keys in subsequent entries. If settlement changes too, the adoption receipt still comes from the outgoing witness; a tagged witness requires a settlement mechanism that accepts it. An exit receipt cannot substitute for §15's witness receipt.

**Founding and deferred details.** A group founded directly under a future mechanism is rejected by a v1 verifier (§5.3); there is no accepted predecessor to preserve or unsupported finding to authenticate. It need not make future signatures intelligible to v1. Future signature layouts, strictness rules, limits, and an algorithm-bound 32-byte actor identifier can apply beyond an established transition, or at such a new founding. They need not rewrite existing entries or change an old verifier's behavior. The amendment does not promise that the current log library already supports them. Nor does this key change make the fixed SHA-256/BLAKE3 commitments post-quantum replacements; those remain separately pinned.

**Agreement.** Design "Keys and algorithms", the new delta requirement, the amended roster and signature requirements, and standard §§2.2, 5, 5.2, 5.3, and 13 agree. The strict Ed25519 requirements describe the v1 mechanisms; the tagged branch reserves representation, not v1 acceptance. Their unreadable-entry rules agree on the prior-authority boundary. No contradiction requires an amendment before implementation.

## Non-blocking notes and validation

- Preserve tests of the transition boundary when the named fixture hooks are filled: a valid old-format adoption, rejection without a valid outgoing receipt, and failure to establish when a future signature is attached. Missing filled vectors are not a blocker for this review.
- The `algorithm-adoption` fixture hook mentions a tagged witness alongside an unknown auth mechanism. Such evidence can establish unsupported without the old verifier validating the opaque policy. A positive fixture for a valid future group's policy should also name a settlement mechanism that accepts that witness.
