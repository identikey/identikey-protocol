Disposition: task-red. The intended sign-in/add split is sound, but the current contract needs the corrections below before act.

## Blind pass

Written from the packet Why, human decisions, living party spec, OIDC grant spec, and the 2026-10-25 learning, before opening design.md or tasks.md.

1. Pin sign-in to credentials.get and require explicit user intent for every credentials.create.
2. Pin successful sign-in to a verified assertion and a currently accepted database credential bound to this party and holder; an id match alone proves nothing.
3. Preserve exact registered origin, party-host rp.id, active-party checks, and ceremony/session binding across both paths.
4. Refuse vault inventory inference: the database records accepted credentials, while cancellation or NotAllowedError cannot establish vault contents.
5. Keep ordinary add duplicate protection through excludeCredentials scoped to the holder and party, with server-side authorization for linking new credentials.
6. Treat the deliberate same-vault second passkey as an explicit exception using a distinct user.name, and examine its interaction with stable user.id and authenticator replacement behavior.
7. Run signalAllAcceptedCredentials only after authentication with the complete accepted set for that user and RP; signaling must not become an authorization decision.
8. Preserve enrollment's K1 pin, nonce/deadline, credential/session binding, and separate IdentiKey proof after either ceremony.
9. Refuse any promotion of passkey sign-in into OIDC URN-grant proof, keyspace membership, capability authority, or certificate revocation.
10. Tradeoff: simple explicit sign-in/add controls avoid speculative vault probing, but users need a recoverable path for stale credentials and intentional additional passkeys.

## Comparison and steelman

Reviewed the prepared contract in proposal.md, specs/identikey-party/spec.md, design.md, tasks.md, and steer.md after saving the blind pass. The proposal records the 2026-10-26 activation and preparation for ikp-hdj. This review applies to that contract, not an implementation.

The author answers the core concerns: explicit create, get for return visits, database-backed credentials, holder/host allow lists, cancellation without create, post-sign-in signaling, and separation from the URN grant and subject-key selection. Retaining the living standard's enrollment and certificate rules is the right scope. A database schema, recovery product, new certificate format, and production browser test are not prerequisites for this amendment.

The strongest case for acceptance is that ordinary WebAuthn validation is implicit, add would naturally appear inside an authenticated account, and the same-vault behavior reflects the observed 1Password experiment. That reading is insufficient for a normative protocol amendment: the positive sign-in scenario explicitly starts a session after the signature check, add has no ownership precondition, and the experiment used a different user.id on each creation. The proposed stable-id flow is materially different. The following requests make those assumptions reviewable without implementing the product.

## Required corrections

### R1 — P1: Define the server acceptance boundary for sign-in

Locations: specs/identikey-party/spec.md:12–18; design.md:25–27.

The current conditions are a credential row at this host and a matching signature. They omit challenge freshness and binding, signed origin verification, and server-side holder binding. A replayed signed response still meets those written conditions. For a named holder H, a valid credential belonging to another holder at the same host also meets them; the client allow list is not a server authorization check.

WebAuthn §7.2 requires account/userHandle and allow-list checks, client-data type/challenge/origin checks, rpIdHash, presence and applicable verification flags, and signature validation. [W3C assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

Require full WebAuthn verification by normative reference, with a fresh server-issued, expiring, single-use challenge bound to this ceremony/session and party. Explicitly bind the session to the verified holder; validate userHandle for discovery and any preselected holder. Preserve the exact registered origin and party status rules. The enrollment nonce in living §5 occurs later and cannot supply sign-in replay protection. Add rejection scenarios for replay, wrong signed origin/RP, another holder at the same host, and mismatched userHandle. These are spec scenarios, not a request to build tests in core now.

### R2 — P1: Authorize attaching a new credential to an existing holder

Locations: specs/identikey-party/spec.md:4–9,32–44; design.md:33–42.

An explicit button proves intent to create a credential, not authority to attach it to H. The contract says to store under H and reuse H's stable id without stating how H is authorized. A caller who merely names an existing holder must not be able to register an attacker-controlled passkey under that holder. excludeCredentials does not establish ownership.

State that adding to an existing holder requires an authenticated, server-bound session authorized for that holder and party; bind the pending registration and its completion to that session. Incorporate WebAuthn registration validation rather than accepting a raw client-submitted credential row. Distinguish first-holder registration from adding to an existing account, without designing a recovery mechanism. Add scenarios rejecting an unauthenticated existing-holder add and a cross-holder/session completion. Both ordinary add and the deliberate same-vault exception need this gate.

### R3 — P1: Reconcile the same-vault promise with stable user.id

Locations: specs/identikey-party/spec.md:32,40–44; design.md:5–9,35–42.

The WebAuthn authenticator model maps discoverable credentials by RP ID and user handle, with at most one per pair; re-registration can replace the existing credential. user.name is not that key. [W3C user-handle definition](https://www.w3.org/TR/webauthn-3/#user-handle).

The local evidence does not resolve this: design.md says the experiment generated a new random user.id for each create, while this delta requires the existing stable id. Therefore the observed second vault item does not establish that the proposed flow retains two usable passkeys. Omitting exclusions and changing the label permits a creation attempt; it cannot support the present unconditional description of another retained passkey.

Preserve the human decisions about an explicit control, omitted exclusions, and a distinct name. Clarify the supported outcome and replacement behavior under the stable-id invariant, and add a scenario for an authenticator that replaces the previous credential. If two simultaneously usable credentials in the same vault are essential, reconcile that requirement with the user-handle contract before act; do not silently randomize user.id or infer success from the old experiment. Any changed handle model must also explain holder lookup and signal grouping. No new host grammar or certificate design is requested.

### R4 — P2: Make signaling a browser-side, best-effort follow-up

Locations: specs/identikey-party/spec.md:47–52; design.md:46–48.

The unconditional endpoint SHALL-call has no unsupported/error path. MDN documents limited browser availability, base64url userId/credential IDs, and a feature-detected browser call. [MDN signalAllAcceptedCredentials](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential/signalAllAcceptedCredentials_static).

Specify that the server supplies the complete accepted set for the authenticated holder/host and the party page invokes the API when available, using the defined encodings. Missing support, rejection, or no authenticator update must preserve successful sign-in and must not trigger create. A failed database read must not masquerade as an empty accepted set. Omitted accepted IDs can cause credentials to be hidden or removed, and successful API completion is not proof that every vault updated. [W3C signal semantics](https://www.w3.org/TR/webauthn-3/#dom-publickeycredential-signalallacceptedcredentials).

Add an unsupported/rejected-signal scenario and a multi-credential scenario proving the signal includes all accepted credentials for H at this host, not just the credential used to sign in. This retains the decided post-sign-in signal while separating maintenance failure from authentication failure.
